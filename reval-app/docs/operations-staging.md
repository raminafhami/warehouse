# راهنمای استقرار آزمایشی و بازیابی REVAL

این راهنما برای آماده‌سازی است. آزمون عملیاتی G7 و تأیید G8 برای شروع پایلوت روی محیط و دادهٔ مصوب در برنامه ثبت شده‌اند.

## محیط و نسخه

- از پروژهٔ مستقل Compose با نام reval-staging، دیتابیس reval_staging و volume مستقل استفاده کنید. پورت Web به loopback میزبان محدود است. TLS را در reverse proxy همان میزبان یا مسیر خصوصی مورد تأیید سازمان خاتمه دهید و مقصد را به پورت loopback هدایت کنید.
- APP_ORIGIN باید دقیقاً origin مرورگر و از نوع HTTPS باشد. فایل تنظیمات حاوی رمز فقط در فضای حفاظت‌شدهٔ محیط نگهداری شود. برای ثبت شواهد از تنظیمات بدون مقادیر حساس استفاده کنید.
- REVAL_IMAGE_TAG را به SHA کامیت انتشار تنظیم کنید. در صورت استفاده از registry خصوصی، REVAL_IMAGE_PREFIX را مشخص و digestهای هر سه image را ثبت کنید. نسخه قبلی و digestها را برای rollback نگه دارید.
- قبل از راه‌اندازی روی محیط مصوب، دستور Compose config --quiet را برای دو فایل compose.yaml و compose.staging.yaml اجرا کنید. بعد از build و start، صفحه، HTTPS، GET /api/v1/health/live، GET /api/v1/health/ready، ورود و audit را از مسیر واقعی بررسی کنید.
- برای تمرین محلی staging، ابتدا npm run build را اجرا کنید. REVAL_QA_MONGOD را روی مسیر mongod و در صورت نیاز REVAL_QA_OPENSSL را روی مسیر OpenSSL تنظیم کنید و node apps/api/test/support/staging-smoke.js را اجرا کنید. این آزمون فرایندها و گواهی کوتاه‌عمر خود را برای loopback می‌سازد.
- seed دمو به‌صورت opt-in مخصوص توسعه و تست است. staging با ALLOW_DEMO_SEED=false بالا می‌آید.

## پایش و رخداد

- از شبکهٔ دسترسی کاربران، HTTPS و readiness را پایش کنید. تجمیع وضعیت ۵xx، زمان پاسخ و خطای replica set را در سامانهٔ پایش مصوب ثبت کنید. آستانه‌ها و دریافت‌کنندهٔ هشدار با D07 و D08 مشخص می‌شوند.
- قطع شبکه یا نتیجه نامعلوم فرمان را ثبت کنید. بعد از برگشت اتصال، همان فرم را بدون تغییر در همان صفحه تکرار کنید و نتیجه را از رکورد و audit بخوانید.
- اگر readiness به‌دلیل DB ناموفق است، برگشت primary، فضای ذخیره‌سازی و خطاهای MongoDB را بررسی کنید. تا تأیید آشتی، عملیات اصلاح دستی انجام نشود.
- در هشدار دیسک، فضای آزاد volume و مقصد backup را بررسی کنید. حذف فایل WiredTiger یا آرشیو حفاظت‌شده از عملیات نگهداری روزمره خارج است.
- هنگام قطع چاپگر، شناسه و نسخهٔ برچسب را از برنامه پیدا کنید. بعد از چاپ مجدد، تأیید بسته‌بندی و کارتن را با اسکن برچسب واقعی کامل کنید.

## پشتیبان و بازیابی

- فایل‌های بارنامه و شواهد همتا به‌صورت BSON در MongoDB ذخیره می‌شوند. پشتیبان باید دیتابیس، مجموعه‌های فایل، ایندکس‌ها و سوابق audit را پوشش دهد.
- برای پشتیبان منطقی با MongoDB Database Tools نسخهٔ سازگار، نوشتن برنامه را متوقف کنید. dump دیتابیس را به‌صورت آرشیو فشرده بگیرید و checksum، نسخه سرور، نسخه ابزار، زمان قطع نوشتن و شناسه انتشار را ثبت کنید. رمز در فایل تنظیمات محدود ابزار قرار می‌گیرد. آرشیو رمزگذاری‌شده در مقصد خصوصی مصوب نگهداری شود. [راهنمای mongodump](https://www.mongodb.com/docs/database-tools/mongodump/)
- برای پشتیبان سرد، اول API و هر نویسندهٔ دیگر را متوقف کنید، سپس MongoDB را کامل و تمیز ببندید. از همهٔ فایل‌های پوشهٔ داده یک آرشیو بگیرید. نسخهٔ تازه را در مسیر دادهٔ خالی و یک نمونهٔ جدا بازیابی کنید. برای مانور محلی، REVAL_QA_MONGOD را روی مسیر mongod تنظیم و node apps/api/test/support/cold-restore.js را اجرا کنید.
- پس از بازیابی، primary و readiness، ورود تازه، بارگیری فایل با checksum و تطبیق موجودی را بررسی کنید. سشن‌های کپی‌شده در محیط متصل به کاربران واقعی پیش از بازگشایی با گردش امنیتی مصوب ابطال شوند.
- فاصلهٔ آخرین نقطهٔ دادهٔ قابل بازیابی تا رخداد را به‌عنوان RPO و زمان بازیابی سرویس و تأیید آشتی را به‌عنوان RTO ثبت کنید. هدف‌های D08 برای محیط واقعی هنوز تعیین نشده‌اند.

## ارتقا و rollback اپلیکیشن

از محیط جدا و پشتیبان تأییدشده شروع کنید. بار اول روی دادهٔ بازیابی‌شده، نصب، migration و مسیر عملیاتی را با image جدید اجرا کنید. برای تمرین محلی با نسخهٔ قبل، REVAL_QA_PREVIOUS_API را روی پوشهٔ apps/api/src نسخهٔ نصب‌شدهٔ قبل تنظیم کنید. پس از ثبت نسخهٔ قبل و بررسی سازگاری migration، در صورت مشکل فقط اپلیکیشن API و Web را با imageهای قبلی راه‌اندازی کنید. دیتابیس موجود فقط در صورتی به اپلیکیشن قبلی متصل شود که خواندن داده و رفتار نوشتن با همان schema بررسی شده باشد. تغییر یا بازگردانی داده به طرح جدا و پشتیبان معتبر نیاز دارد.

### تمرین کانتینری با دادهٔ مصنوعی

در میزبان دارای Docker و Compose، یک checkout جدا از نسخهٔ قبلی آماده کنید. دستور زیر را از ریشهٔ نسخهٔ جدید اجرا کنید.

```text
node apps/api/test/support/compose-upgrade.js PATH_TO_PREVIOUS_CHECKOUT
```

گزینهٔ اجرای دستی گردش `REVAL checks` در GitHub Actions نیز همین تمرین را با تگ یا کامیت نسخهٔ قبلی اجرا می‌کند. تمرین imageهای API و Web هر دو نسخه را می‌سازد، پروژه و volume آزمایشی جدا ایجاد می‌کند و MongoDB را در هر سه مرحله روی همان کانتینر نگه می‌دارد. یک رسید مصنوعی روی نسخهٔ قبلی و یک رسید روی نسخهٔ جدید ثبت می‌شود. پس از بازگشت، هر دو رسید با ماندهٔ اولیه و بدون ثبت مضاعف بازخوانی می‌شوند. خروجی پایانی شناسهٔ imageهای واقعاً اجراشده را ثبت می‌کند. پس از اجرا منابع همان پروژهٔ آزمایشی پاک می‌شوند.

در این تمرین اتصال به Web از loopback است. TLS و ماندگاری نشست در آزمایشگاه بومی جداگانه بررسی می‌شوند. برای پذیرش محیط مقصد، شناسه یا digestهای مصوب، شواهد HTTPS و صورت‌جلسهٔ ارتقا و بازگشت باید در همان محیط ثبت شوند.

## پایلوت

فرم پذیرش D09 باید خط، مدل، کاربران و مسئولان تولید و کیفیت، موجودی اولیه با شاهد، مدت اجرا، روش تطبیق روزانه و معیار توقف را داشته باشد. اختلاف توضیح‌نداده‌شده در آشتی روزانه به مسئول پذیرش ارجاع می‌شود. شواهد نرم‌افزار با برنامه و ثبت عملیاتی محل پایلوت تکمیل می‌شوند.
